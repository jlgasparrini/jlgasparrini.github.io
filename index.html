Aboutme

I've been writing software professionally since 2013, mostly with Ruby on Rails and React. The work I'm best at is the kind where a mistake costs money: checkout, payments, data that has to stay in sync across systems, and search that has to stay fast under load.

I like clean, maintainable code the next person can change safely, technical decisions backed by data, and seeing the result in front of real users. I've worked remotely with teams in the US, Spain and Uruguay since 2017, across e-commerce, publishing, government and SaaS.

Since mid-2026 I've worked AI-first at SWARE: agents write the code, and I own the architecture, the review and what reaches production. It's the same judgement I built on checkout and payments, applied at a much faster pace.

These days I care most about performance and developer experience: fast pages, and codebases people aren't afraid to touch.

From ticket to production with Claude Code

SWARE, for Elefta, 2026

We built an internal framework around Claude Code that takes a ticket all the way to a pull request. It gathers the context Claude needs for the task and generates the code under the company's rules and conventions. I review it and open the PR, another developer reviews it, and it goes to staging for QA before production.

The review and QA gates stayed the same; the pace didn't. Work that used to take months now ships in days.

One checkout for a group of marketplaces

GOAT Group, 2020 to 2025

GOAT Group grew by merging companies, and each one came with its own checkout. We replaced them with a single master checkout that every platform redirects to. My part was making carts work across platforms: the validations and rules each brand needed, so nothing a business team relied on got lost in the merge.

Payments were only partly integrated when I started on them. Finishing those integrations was the work I enjoyed most there.

  • Ruby on Rails
  • React
  • PostgreSQL
  • Sidekiq

Making search fast again

GOAT Group

Search was slow at times, and no single cause explained it. It was a mix of N+1 queries, Elasticsearch indexes drifting out of sync with the database, and very little caching. We fixed the query patterns, made index syncing reliable and added caching where reads dominated.
